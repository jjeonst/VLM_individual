# PR2L Habitat ObjectNav 재현 계획

> 이 파일이 계획의 정본이다. `~/.claude/plans/recursive-greeting-finch.md`에 같은 내용의
> 사본이 있으나 그쪽은 작업 도구가 만든 것이므로, 변경은 이 파일에 한다.
>
> 구현하면서 확정되는 모델 구조와 세부값은 이 계획서가 아니라
> **`IMPLEMENTATION.md`** 에 따로 쌓는다. 계획서는 "무엇을 왜 이렇게 하기로 했는가"를,
> 구현서는 "실제로 무엇이 들어갔는가"를 담는다.

## Context

**무엇을 하려는가.** 논문 *Vision-Language Models Provide Promptable Representations for
Reinforcement Learning* (Chen, Mees, Kumar, Levine, [arXiv:2402.02651](https://arxiv.org/abs/2402.02651),
저장소 사본 `docs/papers/PR2L_arxiv_2402.02651.pdf`)의 **Habitat ObjectNav 모방학습 실험**
(본문 Table 3)을 이 환경에서 그대로 재현한다.

**왜 하는가.** 이 저장소는 지금까지 PR2L을 참조해 왔지만, 실제 구현은 여러 곳에서 논문과
갈라져 있었다. 텍스트 토큰을 4개로 풀링했고, 주성분분석의 적용 순서가 달랐으며, 시간축이
LSTM이 아니라 인과 마스킹 Transformer였고, 시각 백본 해상도가 224 px이 아니라 384 px이었다.
각각은 그럴듯했지만 합쳐 놓으면 논문 수치와 비교할 수도, 차이가 났을 때 원인을 짚을 수도
없었다. 이번에는 **논문이 명시한 것은 그대로 따르고, 논문이 침묵한 것은 원 출처에서 값을
찾아 근거와 함께 기록**한 뒤 구현한다.

**결과로 무엇을 얻는가.** 논문 Table 3(검증 2000 에피소드 평균 성공률 41.9 %)과 직접 비교
가능한 재현 수치 하나, 그리고 "논문과 일치 / 의도적 이탈 / 논문 미명시(사용자와 합의)"로
분류된 사양 대조표.

## 1. 확정된 사양

### 1.1 논문이 명시한 것 — 그대로 따른다

> **표를 읽을 때 주의.** 부록 C.2는 두 부분으로 나뉜다. 앞의 7개 항목은 조건 전체에 걸리고
> ("we adopt many of the same design choices... but with a few critical differences"),
> 뒤의 5개는 `"For PR2L-specific design choices:"` 아래에 있어 **PR2L 조건에만** 걸린다.
> 아래 표에서 후자는 **[PR2L 조건 전용]**으로 표시한다. 이 구분을 흘리면 PCA와 입력 폭을
> 파이프라인 전체의 상수로 착각하게 되고, 실제로 한 번 그렇게 됐다(§1.4).

| 시각 토큰 | 256개(16×16) | 부록 C.2 PR2L 1 |
| VLM 학습 | **없음 (완전 고정)** | 본문 3.1 |

| 디코딩 | 샘플링, **디코딩 직전 시드 고정**, **temperature 0.4**, **32–48 new tokens** | 부록 C.2 PR2L 4 |
| 사용 층 | 마지막 **2개 층** | 부록 C.2 PR2L 3 |
| 사용 위치 | 시각 + 질문 + 생성 답변 **전 위치** | 본문 3.1, 부록 I Listing 2 |
| 시각 풀링 | 표현 추출 **후** 4×4 평균 풀링 → 16 토큰 | 부록 C.2 일반 5, Listing 2 주석 |
| 차원 축소 | **[PR2L 조건 전용]** PCA **4096 → 1024** (궤적당 1프레임 무작위 표본으로 적합) | 부록 C.2 **PR2L** 2 — "To reduce the size of VLM representations **for PR2L**" |
| 층 결합 | **[PR2L 조건 전용]** 토큰마다 두 층을 특징축으로 **stack → 2048** | 부록 C.2 **PR2L** 3 |

| 대조군 입력 폭 | 정책 입력 투영은 `Linear(tf_embed_dim → 1024)`이고 **조건마다 이 값만 바뀐다** | 부록 I Listing 1이 `tf_embed_dim`을 생성자 인자로 둠 |

| 관찰 | RGB(480,640,3) + 위치(2) + 나침반(1) + 직전행동 one-hot(4) + 목표 one-hot(6). **깊이 제외** | 부록 C.1 |

### 1.2 논문이 침묵 — 원 출처에서 찾아 사용자와 합의한 것

| 항목 | 채택값 | 근거 |
|---|---|---|
| LSTM 은닉 크기 | **2048** (2층) | PR2L 부록 C.2가 이탈 사항 7가지를 열거하면서 순환망 폭을 넣지 않음 → 선행 연구값 유지. PIRLNav([arXiv:2301.07302](https://arxiv.org/abs/2301.07302)) §3이 "2층 2048-d"로 명시. 파라미터 약 59 M |
| 비시각 관찰 임베딩 | 위치 → FC 32-d, 나침반 → FC 32-d, 목표 one-hot → FC 32-d, 직전행동 → 32-d | PIRLNav §3 |
| 옵티마이저 | **AdamW, weight decay 1e-6** | VC-1([arXiv:2303.18240](https://arxiv.org/abs/2303.18240)) 부록 A.3 |
| 스케줄러 | 선형 감쇠, **전체 길이를 400M 전이로 가정**하고 40M에서 중단 (→ 학습률이 약 10 %만 내려감) | PR2L 부록 C.2 4의 문장을 그대로 구현 |
| 배치 크기 | **16,384 전이** | VC-1 부록 A.3의 400M 전이 / 25,000 업데이트 / 512 병렬환경에서 유도. PR2L 본문의 "24k gradient steps ≈ 400M"과 일치 |

> **정정 (2026-08-22).** 이 표에 한때 "정책 Transformer — nhead 8"이 있었다. 부록 I의
> Listing 1을 다시 읽은 결과 `torch.nn.Transformer(1024, 1, ...)`로 **헤드 수가 명시**돼
> 있었으므로 §1.1로 옮기고 값을 1로 고쳤다. 헤드 수는 `nn.Transformer`의 파라미터 수를
> 바꾸지 않으므로(1이든 8이든 78,717,476개) 정정 비용은 없었다. 8은 `num_heads=8`로 남겨
> 두었고, 재현이 끝난 뒤의 실험 대상이다 — 헤드가 여럿이면 하나는 시각 토큰에, 다른 하나는
> 생성된 문장에 붙을 수 있어 유리할 여지가 있다.

### 1.3 논문 부록의 오기

부록 C.1은 목표 물체 one-hot 크기를 **3**으로 적었으나, 본문과 Table 3은 6종(변기·침대·
소파·의자·TV·화분)이고 검증 2000 에피소드가 6종에 걸쳐 있다. 부록 D의 단순화 설정(3종)
값이 잘못 들어간 것으로 보고 **6**을 쓴다.

### 1.4 이 표를 처음 만들 때 저지른 읽기 오류 두 가지

둘 다 실행 전에 잡혀 비용은 0이었지만, 원인이 같은 종류라 남긴다. **논문을 찾던 값만 보고
읽었고, 같은 자리에 있던 다른 값과 그 값이 걸리는 범위를 흘렸다.**

**오류 1 — 조건별 값을 파이프라인 상수로 적었다.** PCA(4096→1024)와 입력 폭(2048)을 근거
칸에 "PR2L 2", "PR2L 5"라고 적어 놓고도 값 칸에는 조건 표시 없이 적었다. 그래서 대조군을
설계할 때 "이미지 인코더는 2176인데 입력이 2048로 고정이니 어떻게 맞추나"라는, 성립하지
않는 문제를 만들어 냈다. 실제로는 PCA가 PR2L 전용이고 입력 폭은 Listing 1의 생성자 인자다.
**§1.1 표 머리말의 [PR2L 조건 전용] 표기가 이 오류에 대한 대책이다.**

**오류 2 — 인용한 코드를 끝까지 읽지 않았다.** §1.2에 nhead를 "논문 미명시"로 적으면서
그 근거를 이렇게 썼다:

> ff는 논문이 Minecraft(512:512)와 **Listing 1(1024:1024)** 모두에서 지킨 1:1 비율 유지

즉 `torch.nn.Transformer(1024, 1, num_encoder_layers=1, num_decoder_layers=1,
dim_feedforward=1024, batch_first=True)`에서 1·3·4·5번째 인자를 읽어 인용해 놓고 **2번째
인자(nhead)만 건너뛰었다.** 그리고 그 자리에 "논문이 침묵하므로 8로 확대한다"는 근거를
직접 써 넣었다. 없는 자유를 발명한 셈이다.

**대책.** 논문의 코드 목록(Listing 1·2·3)은 값을 찾을 때가 아니라 **한 번에 전부** 읽고
항목별 대조표로 남긴다. Listing 1은 IMPLEMENTATION.md §3.1에, Listing 3(`argmax`)은 §5에
대조표가 있다. Listing 2는 Minecraft용(층을 concatenate)이라 Habitat과 다르며, 이 차이는
부록 C.2 PR2L 3이 명시한다 — 우리는 stack을 쓴다.

## 2. 데이터 — Habitat-Web 사람 시연 (논문과 동일)

### 2.1 출처와 확인된 사실

[huggingface.co/datasets/axel81/pirlnav](https://huggingface.co/datasets/axel81/pirlnav)의
`objectnav_hm3d_hd` (PIRLNav이 배포하는 ObjectNav-HD). 라이선스 CC BY-NC 4.0.

- 80개 장면 shard, **총 86.9 MB** (행동 열만 저장, RGB 없음)
- 표본 shard(`1S7LAXRdDqK`) 직접 검증: 에피소드 1,134개, 평균 151.3 스텝, 중앙 95, 최대 854,
  목표 6종, `is_thda` 전부 `null`(**합성 증강 없는 순수 사람 시연**), AMT 작업자 276명
- 평균 151 스텝은 논문의 "사람 기준 150+ 스텝"과, 77k × 151 ≒ 12M는 "77k trajectories
  (12M steps)"와 일치 → 논문이 쓴 바로 그 데이터
- **80개 장면 자산이 전부 로컬에 있음**을 이름 대조로 확인 (`scene_datasets/hm3d/train/`,
  navmesh·semantic 포함, 누락 0개)
- **재렌더링 코드가 이미 있음**: `topovlm_data/habitat_web_render.py`,
  `topovlm_data/habitat_web.py`, `configs/data/pr2l_habitat_web.yaml`.
  다만 현재 MP3D 경로를 가리키므로 HM3D로 바꿔야 한다.

### 2.2 부표본 — 논문과 동일하게 7,550 궤적

부록 C.2 항목 1의 문장을 그대로 구현한다.

> "we used a subset of the dataset, built by dividing the dataset by both target object and
> scene, then **sampling every tenth demo**. This would ensure that our training data still
> contained examples from every training scene + target object combination that existed."

두 가지가 여기서 확정된다. 묶는 단위는 장면이나 물체 하나가 아니라 **(장면, 목표 물체) 쌍**
이고, "every tenth"는 무작위 추출이 아니라 **고정 간격**이므로 시드가 없고 몇 번을 돌려도
같은 결과가 나온다. (이 항목은 한때 "논문 미명시"로 분류했으나 원문 확인 결과 명시돼
있었다. §1.2가 아니라 §1.1에 속한다.)

조합별로 먼저 나누는 이유는 논문이 바로 다음 문장에 적어 두었다. 전체를 대상으로 그냥
10분의 1을 뽑으면 예시가 하나도 남지 않는 조합이 생기고, 그러면 정책은 학습 때 본 적 없는
물체를 그 건물에서 찾으라는 요구를 받게 된다. 따라서 **"조합 누락 0"은 보고용 통계가 아니라
통과해야 하는 조건**으로 취급한다.

### 2.3 저장 — 비압축, `/data`

프레임당 크기를 표본 200궤적으로 실측한 결과 **정확히 900 KB**(480×640×3 uint8, 압축 없음)
였다. 따라서 1.1 M 스텝의 RGB는 **약 990 GB**다.

| 산출물 | 프레임당 | 총량 |
|---|---|---|
| RGB (1단계) | 900 KB | 990 GB |
| 임베딩 — PR2L + CoT (약 76토큰 × 2048 × 4B) | 622 KB | 684 GB |
| 임베딩 — PR2L, CoT 없음 | 622 KB | 684 GB |
| 임베딩 — 이미지 인코더 (16토큰) | 131 KB | 144 GB |
| | | **약 2.5 TB** |

**저장 위치는 `/data/topovlm/habitat/` (저장소에서는 `data/habitat/`), 압축하지 않는다.**
계산 노드에서 보이는 유일한 큰 공유 볼륨이고(88 TB 중 68 TB 여유), 큰 파일 순차 읽기에서
`/scratch`보다 빠르다([[nfs-vs-scratch-io]]: 866 vs 552 MB/s). JPEG 등 손실 압축은 VLM
입력 자체를 바꾸므로 쓰지 않는다.

**RGB는 중간 산출물이다.** 인코딩 3종이 모두 끝나고 검증되면 지운다. 그때까지 붙들고 있는
이유는 조건마다 프롬프트가 달라 임베딩을 공유할 수 없고, 저장하지 않으면 같은 장면을 세 번
다시 렌더링해야 하기 때문이다. 최대 점유 2.5 TB, 이후 정상 상태 1.5 TB.

### 2.4 렌더링 방식

`reference_replay`는 행동만 담고 `agent_state`가 `null`이다. Habitat의 관찰·행동·동역학이
결정적이므로(부록 C.1), 에피소드의 `start_position`/`start_rotation`에서 시작해 행동 열을
재생하면 RGB와 자세가 모두 정확히 복원된다.

### 2.5 쓰지 않는 데이터 — 이유를 남긴다

- **로컬 `sources/habitat_web_hf_metadata`**: MP3D THDA 70k. 전수 분석 결과 56장면 /
  70,176 에피소드 중 **10,091개가 합성 THDA**이고 목표가 **28종**이다. 논문의 HM3D 6종 설정이
  아니며, MP3D 장면 자산도 예제 1개만 있고 별도 동의 절차가 필요하다.
- **기존 `pr2l_hm3d_objectnav`** (6,000궤적 / 333 k 스텝 / RGB 303 GB): 출처가
  `hm3d_objectnav_shortest_path`, 즉 목표 좌표를 아는 최단 경로 추종기라 평균 55.5 스텝으로
  끝나고 라벨에 탐색 행동이 없다. 논문 Table 3과 같은 것을 재지 못한다.
  (참고로 이 데이터에는 길이 ≤1 궤적이 961개(16 %) 있고, 검증 매니페스트의 `scene_id`에
  `data/habitat/scene_datasets/`가 두 번 들어간 경로 버그가 있다.)

### 2.6 공통 주의

- **위치·나침반**: RGB를 렌더링하는 같은 재생 과정에서 매 스텝의 좌표와 방위각을 함께
  기록한다. 직전 행동은 행동 배열에서 바로 유도한다. 별도 단계가 필요 없다.
- **기존 임베딩 `embeddings/pr2l_hm3d_bc/`(5.5 GB)는 재사용하지 않는다.** 세 가지가 다르다 —
  (1) 토큰이 16개뿐이라 질문·생성 텍스트 위치가 없음, (2) PCA가 8192→1024로 층을 먼저 쌓았고
  논문은 4096→1024 후 stack하여 2048, (3) `frame_stride=4`로 네 프레임에 하나만 남긴 위상
  그래프 형식. 데이터 자체도 최단경로 출처라 바뀐다.

## 3. 구현 순서

각 단계는 앞 단계의 산출물만 필요로 하므로 순서대로 검증하며 진행한다.

0. **데이터 확보와 부표본 선정** — `vlm_topology_test/phase4/subsample.py`.
   CPU만 사용, slurm 불필요.
   (파일 이름은 `select.py`로 두면 안 된다 — 표준 라이브러리 `select` 모듈을 가려
   `huggingface_hub` 임포트가 깨진다.)
   - `objectnav_hm3d_hd` 80 shard(86.9 MB)를
     `/data/topovlm/habitat/sources/pirlnav_hf/objectnav_hm3d_hd/train/content/`로 내려받는다.
   - **1차 검증 — 내려받은 것이 논문이 쓴 데이터인가**: 총 궤적 77 k, 총 스텝 12 M,
     평균 길이 159, 장면 80, 목표 6종(각 ±20 %, 장면·물체는 정확히). 어긋나면 멈춘다.
   - §2.2의 규칙대로 (장면, 물체) 조합별 stride 10으로 선정.
   - **2차 검증 — 부표본이 논문과 같은가**: 궤적 약 7,550, 스텝 약 1.1 M(각 ±20 %),
     장면 80, 목표 6종, **조합 누락 0**. 어긋나면 선정 파일을 쓰지 않고 멈춘다.
   - 산출물: `episode_selections/pr2l_habitat_web_hd/train_every_tenth.jsonl`
   - **평가용 데이터도 이때 함께 받는다**: 로컬에는 ObjectNav HM3D **v2**판만 있는데
     (`datasets/objectnav/hm3d/v2/`, 검증 36장면), 사람 시연은 v1 장면을 참조하고 논문의
     "검증 20장면 2000 에피소드"도 v1 기준이다. `objectnav_hm3d_v1`을 따로 받아야 5단계를
     논문과 같은 조건으로 돌릴 수 있다.
1. **재생 렌더링** — `topovlm_data/habitat_web_render.py`로 궤적별 RGB `(T,480,640,3)` uint8과
   행동 `(T,)`을 만들고, **같은 재생에서 매 스텝 `(x, y, yaw)`도 함께 기록**한다.
   `nav_baseline/env.py`의 `open_scene`/`reset_to`/`ACTION_NAME`을 재사용한다.
   검증: 마지막 스텝의 위치가 목표 관찰 지점 0.1 m 이내인 비율(사람 시연이므로 높아야 함),
   그리고 소량 표본으로 먼저 돌려 1.0 TB 전체 소요 시간을 추정.
2. **VLM 인코딩** — `encoders/prismatic.py`를 224 px·전 토큰 위치 반환으로 맞춘다.
   프레임당 `[16 + 질문토큰 + 32~48, 4096] × 2층`을 얻고, 층별 PCA(4096→1024) 적용 후 stack →
   `[N, 2048]`. PCA는 궤적당 1프레임 표본으로 먼저 적합해 저장하고 이후 고정.
   검증: 같은 프레임을 다른 목표로 인코딩했을 때 시각 토큰이 동일한지, 텍스트 토큰이 다른지.
3. **정책** — 1.1·1.2의 사양대로 구현. `Linear(2048→1024)` → CLS Transformer → 비시각 임베딩
   결합 → 2층 2048 LSTM → 4-way. 가변 토큰 수를 위한 패딩 마스크 필수.
   검증: 파라미터 수가 Transformer 약 16.8 M + LSTM 약 59 M인지 확인.
4. **학습** — AdamW(lr 1e-4, wd 1e-6), 400M 기준 선형 감쇠 스케줄, 궤적 단위 배치 16,384 전이
   (gradient accumulation), 40 epoch, inflection + 정지·회전 1.5배 가중.
5. **평가** — 미지의 검증 장면에서 폐루프 롤아웃. 성공 = 목표 관찰 지점 0.1 m 이내 자발적 STOP.
   목표 물체별로 나눠 보고하고, **출발 측지거리 0–2 / 2–4 / 4–6 / 6+ m 구간별 성공률도 함께
   낸다** (전체 성공률 하나로는 먼 에피소드의 붕괴가 가려진다).
   - **장면 메시는 실행 노드의 `/scratch`로 캐시한다.** 평가는 에피소드마다 장면을 열고
     닫으므로 메시 적재가 반복되는데, 이건 작고 무작위한 읽기가 많은 패턴이라 NFS 왕복
     지연이 지배한다([[nfs-vs-scratch-io]]의 실측에서 장면 캐시가 13.5초 → 0.1초).
     반대로 RGB·임베딩처럼 큰 파일을 통째로 훑는 것은 `/data`가 더 빠르므로 옮기지 않는다.
6. **대조군** — 논문 Table 3의 세 조건 중 우리가 재현하는 두 가지.

   | 조건 | Table 3 | 표현 | 정책 입력 폭 |
   |---|---|---|---|
   | PR2L + CoT | 41.9 % | 시각 16 + 질문 21 + 생성 32~48 | 2048 |
   | PR2L CoT 없음 | 27.8 % | 시각 16 + 질문(짧음) | 2048 |
   | VLM 이미지 인코더 | 11.6 % | 시각 백본 패치만, 4×4 풀링 후 16 | **2176** |

   이미지 인코더 조건의 사양은 논문이 세 문장으로 확정한다.
   - **PCA를 적용하지 않는다.** 부록 C.2의 PCA 항목은 "For PR2L-specific design choices"
     아래에 있고, 문장도 `"To reduce the size of VLM representations for PR2L"`로 시작한다.
   - **4×4 평균 풀링은 적용한다.** 부록 C.2 일반 5는 "policies that receive visual
     observations as a sequence of tokens"에 걸리는 규칙이고, 이 조건이 정확히 그것이다.
   - **입력 폭은 2176.** `dinosiglip-vit-so-224px`는 DINOv2 ViT-L(1024)과
     SigLIP SO400M(1152)을 이어 붙이고(`dinosiglip_vit.py`의 `embed_dim`), 패치는 256개다.
     Listing 1의 `tf_embed_dim`에 이 값을 넣으면 되고, 그 뒤 d_model 1024부터는 전부 동일하다.
     층 stack(→2048)은 PR2L 전용 항목 3이므로 적용하지 않는다(층이 하나뿐이다).

   **정책 구조는 셋 다 동일하게 유지** — 부록 C.2 일반 5가 명시한 통제 조건이다. 입력
   투영의 폭만 조건에 따라 달라지는데, 그것이 Listing 1이 `tf_embed_dim`을 인자로 둔 이유다.

   **논문이 통제하지 않은 것 하나는 결과에 함께 적는다.** 부록 D는 "Habitat에서는 시각
   임베딩 열이 길수록 성능이 좋은 경향"을 관찰하고 단순화 설정에서는 길이를 맞췄으나,
   본문 Table 3에서는 맞추지 않았다(이미지 인코더 16토큰 vs PR2L 70~85토큰). 따라서
   41.9 대 11.6에는 프롬프팅 효과와 열 길이 효과가 섞여 있다. 반면 41.9 대 27.8은 양쪽 다
   질문 토큰을 가지므로 이 교란에서 비교적 자유롭다.

## 4. 검증

- **단위**: PCA 적합/적용의 왕복 오차, 패딩 마스크가 있을 때와 없을 때 CLS 요약이 달라지는지,
  inflection 가중이 행동 전환 지점에만 붙는지.
- **통합**: 소규모 표본(장면 2개)으로 1~5단계를 끝까지 한 번 통과시켜 성공률이 0이 아닌지 확인.
- **논문 대조**: 최종적으로 §1.1/§1.2/§2의 각 항목을 "일치 / 의도적 이탈 / 논문 미명시"로
  분류한 표를 문서에 남긴다.

## 5. 알려진 위험

- **VLM 인코딩을 세 번 해야 한다.** 대조군 1·2번은 프롬프트가 달라 임베딩을 공유할 수 없다.
  즉 1.1 M 프레임 인코딩이 두 번(CoT 有/無), 생성이 없는 이미지 인코더가 한 번이다.
  논문은 A5000 16대를 썼다.
- **평가가 학습 데이터 인코딩과 맞먹는다.** 5단계는 폐루프라 **매 스텝 VLM을 호출**한다.
  검증 2000 에피소드 × 스텝당 1회이고 실패 에피소드는 최대 500스텝까지 간다. 조건 3개면
  학습용 인코딩과 비슷한 규모의 연산이 평가에만 한 번 더 든다. 논문이 "데이터 생성과 평가는
  A5000 16대로 병렬화했다"고 적은 이유가 이것이다.
- **위 두 가지는 1·2단계 파일럿에서 프레임당 시간을 실측한 뒤 합산해 보고한다.** 그 숫자가
  나오기 전에는 검증 에피소드 수나 조건 수를 줄이지 않는다. 미리 줄이면 논문 비교 가능성만
  잃고 얼마나 절약되는지도 모르는 채로 결정하는 셈이다.
- **임베딩 dtype이 논문에 없다.** float32면 1.5 TB, float16이면 0.77 TB로 두 배 차이가 난다.
  2단계 착수 전에 사용자와 정한다.
- **논문이 재현되지 않을 경우의 판별.** §1.2의 6개 항목(논문 미명시분)이 가장 유력한 원인
  후보이므로, 결과가 어긋나면 이 항목들부터 하나씩 흔들어 본다.

## 6. 남은 작업 (2026-08-23 기준)

### 6.0 목표가 바뀌었다 — 재현이 아니라 구현 가능성

사용자가 목표를 분명히 했다: **논문의 모델을 그대로 구현할 수 있는지 판별하는 것**이지 논문의
수치를 재현하는 것이 아니다. 여기에 조금씩 변화를 주어 새 연구를 진행할 예정이다.

이 목표가 조건 선택을 바꾼다.

| 조건 | 결정 | 이유 |
|---|---|---|
| **PR2L + CoT** | **진행** | 논문의 모델 그 자체 |
| **이미지 인코더** | **진행** | 새 코드 경로(LLM 우회, 폭 2176, PCA·stack 없음)를 요구하므로 구현 능력을 실제로 증명한다. 값도 싸다 |
| PR2L CoT 없음 | **보류** | **새 코드가 0줄.** `build_prompt`가 고르는 문자열 하나만 다르고 추출·풀링·PCA·stack·정책이 전부 같은 경로를 탄다. 구현 능력을 더 증명하지 않는다 |

보류이지 취소가 아니다. 두 가지 때문에 되살릴 값이 있다 — 앞으로의 연구가 프롬프트를 바꾸는
쪽이라면 CoT 없음은 **논문에 정답(27.8 %)이 적힌 유일한 눈금**이고, 검증 장면 숫자 하나만으로는
"구현이 맞고 학습이 부족"과 "구현이 미묘하게 틀림"을 가를 기준이 없다. **CoT > CoT 없음이라는
순서**는 절대값보다 강한 진단이다.

### 6.1 평가 규모: 검증 500 에피소드

논문은 2,000이다. A단계 실측으로 에피소드당 303초가 나왔으므로 2,000이면 조건당 168 GPU-시간,
500이면 42 GPU-시간이다. 재려는 격차가 30 %p인데 500의 표준오차는 2.2 %p라 판정에 충분하다.

### 6.2 순서와 상태

| # | 작업 | 상태 | 규모 |
|---|---|---|---|
| 1 | CoT 인코딩 (7,824궤적) | **진행 중** (10330, 12샤드) | 약 19h / rtx3090 ×4 |
| 2 | 이미지 인코더 인코딩 | **진행 중** (10339, 6샤드) | 15 GPU-h, 22.5 프레임/s 실측 |
| 3 | CoT 학습 | 대기 | 40 epoch, 약 11h |
| 4 | 이미지 인코더 학습 | 대기 | 토큰이 16개뿐이라 더 빠름 |
| 5 | 검증 장면 평가 ×2조건 | 대기 | 500 에피소드, 조건당 약 42 GPU-h |
| 6 | **PCA 그림** | **보류** (§6.3) | 롤아웃은 완료, 인코딩부터 남음 |

`--split val`, `--max-scenes` 미사용이 5번의 조건이다. `--max-scenes`는 A단계 점검용이고
검증 실행에서는 다양성이 요점이다.

### 6.3 PCA 그림 — 설계는 확정, 실행만 보류

**롤아웃은 다시 만들어야 한다.** 처음에 "28궤적 / 2,304프레임, 도달 28/28"로 적었으나
점검 결과 두 가지가 틀렸다.

1. **파일명 충돌로 3궤적이 사라졌다.** 이름을 `{물체}_{episode_id}`로 지었는데 episode_id는
   장면마다 1부터 다시 시작한다. 매니페스트 28행 / 고유 이름 25 / npz 25개이고 실제 프레임은
   2,304가 아니라 **2,063**이다. `toilet_9`는 매니페스트에 500스텝으로 적혀 있는데 저장된
   배열은 27스텝이다 — 서로 다른 두 궤적이 같은 파일을 놓고 덮어썼다. 매니페스트는 28행이
   그대로 남아 겉으로는 정상으로 보였다. **이름에 장면 키를 넣어 재실행한다.**
2. **추종기가 최단으로 가지 않은 궤적이 있다.** `start_geodesic` 대비 실제 이동거리의 비가
   toilet_28 0.25, sofa_32 0.38, toilet_60 0.38, sofa_6 0.42로 6/25가 0.5 미만이다. 회전은
   이동거리에 잡히지 않으므로 회전 탓이 아니고, 추종기가 거리를 잰 인스턴스가 아닌 다른
   관찰 지점을 향한 것으로 보인다. 그림의 색이 "near-optimal policy 하의 가치"인데 궤적이
   near-optimal이 아니면 색이 거짓이 된다. **추종기가 실제로 겨눈 목표까지의 거리를 기록**
   하도록 고치거나 효율 0.5 미만을 버린다.

재실행 비용은 2~3분이다. 논문의 "thirty episode rollouts"에 맞춰 장면 풀을 넓혀 30개를 채운다.

**남은 것**: 같은 프레임을 세 번 인코딩하고 그림을 그린다. 모두 bf16 카드가 필요하고,
지금은 1·2번이 전부 점유하고 있다.

| 인코딩 | 쓰임 | 비용 |
|---|---|---|
| CoT 프롬프트 | 그림 A 위 행 | 약 10분 |
| `"What room is this?"` | 그림 B 위 행 + **두 그림의 방 이름 상자** | 약 10분 |
| 이미지 인코더 | 두 그림 아래 행 | 약 2분 |

**그림 두 장**: A는 위 행이 우리 CoT 조건(실제 쓰는 조건이 방 별로 갈리는가), B는 위 행이
`"What room is this?"`(Figure 8과 직접 대조).

**방법**: 부록 H.1이 문장으로 정해 놓았다 — "we then perform principal component analysis
(PCA) on the **tokenwise average of all embeddings for each observation**, thereby projecting
the embeddings to a 2D space with maximum variance." H.2가 "we conduct a **similar** analysis
on the Habitat data"라고 하므로 그대로 걸린다. 즉 **모든 토큰 위치의 평균**이고, 우리가 고를
자리가 아니다. PR2L은 78토큰×2048 → 2048, 이미지 인코더는 16토큰×2176 → 2176이 된다.
패널마다 독립적으로 2차원 PCA를 적합한다(Figure 8의 축이 패널마다 따로 붙어 있다).

**색 — 논문의 정의를 그대로 쓰면 그림이 뒤집힌다**

논문은 "value under Habitat's built-in oracle shortest path follower"로 칠하고 캡션은
"find toilet에서 고가치 관찰이 화장실로 분류된다"고 읽는다. 즉 **고가치 = 목표 근처**여야
한다. 그런데 부록 D.1의 보상(정지 시 +10·SPL, 이동마다 측지거리 감소분)과 부록 D.2의
γ=0.99로 실제 롤아웃에서 할인 수익을 계산하면 반대가 나온다.

| 색 정의 (γ=0.99) | 남은 거리와의 상관 |
|---|---|
| 논문 문자 그대로 (shaping ×1) | 피어슨 **+0.685**, 스피어만 +0.786 |
| shaping ×0.1 | +0.112 |
| 종료 보상만 | +0.011 |

**이 절에 원래 적어 두었던 근거가 틀렸다.** "potential-based shaping이므로 가치가 남은
거리의 단조감소 함수"라고 썼는데, Φ = −d 인 potential-based shaping은
`V_shaped = V_task + d`가 되어 거리에 **비례해 커진다**. shaping 보상이 조밀해서 멀리서
출발할수록 더 많이 걷어가기 때문이다.

세 번째 줄도 중요하다. shaping을 아예 빼도 상관이 0인데, **궤적 안에서는 음의 관계지만
여러 궤적을 겹치면 상쇄되기 때문**이다 — 짧은 에피소드의 먼 상태가 긴 에피소드의 가까운
상태보다 가치가 높다. 할인 수익은 에피소드 상대적인 양이라, 한 패널에 열 개 에피소드를
겹쳐 놓는 이 그림에서는 의미가 무너진다. 남은 측지거리는 에피소드 간에 뜻이 같다.

**결정(사용자)**: 같은 PCA 좌표 위에 **두 가지 색을 모두** 그린다 — (가) 남은 측지거리,
(나) 논문 문자 그대로의 γ=0.99 할인 수익. PCA는 한 번만 적합하므로 추가 비용이 거의 없고,
논문의 정의가 왜 서사와 어긋나는지를 그림으로 보일 수 있다.

**논문과 남는 차이 하나**: Figure 8은 부록 D의 단순화 설정이라 VLM이 **InstructBLIP**이다.
우리는 본문 실험의 Prismatic을 쓴다. 글자 그대로 재현하려면 다른 모델을 받아야 하는데, 그건
**다른 모델을 검증하는 일**이라 목표에서 벗어난다. 데이터(최단경로 롤아웃 30개)·물체 3종·
방법(토큰 평균 후 PCA)·상자(방 이름)는 논문과 같다.
